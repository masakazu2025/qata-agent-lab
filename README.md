# qata-agent-lab

qata をまるごとコピーし、それを材料に、AI エージェントへの指示（ルール・スキル・レビュー役のエージェント・決めたことなどの文書）の書き方だけを改善する場所です。

- 元のプロジェクト：[masakazu2025/qata](https://github.com/masakazu2025/qata)（Windows のデスクトップアプリに対して、日本語の手順からテストを作り、自動で再生し、結果を確認するツール）
- 立ち上げの issue：[masakazu2025/qata#71](https://github.com/masakazu2025/qata/issues/71)
- 方針の元になったメモ：[plan.md](plan.md)

## なぜ分けたか

qata では、アプリの実装と、エージェントへの指示の改善を同じリポジトリで同時に進めてきました。その結果、指示の手直しに時間を取られて実装が止まりがちになり、どちらも速く進みませんでした。また、スキル・レビュー結果・issue が、人が読むと分かりにくい文になっていました。

そこで、実装は qata でいまの形のまま進め、指示の書き方の改善はここで切り離して進めます。

## qata との関係

- **同期しません。** ここにあるのは、2026-11-19 時点のコピーです。以降、qata の変更は取り込みません。
- **qata に戻すのは必須ではありません。** うまくいけば、改善した中身を qata に手で反映します。場合によっては、ここで作った指示一式に文書を移して、qata を作り直すことも考えます。
- コードも含めて全部コピーしたのは、量がないと、作った書き方の決まりがいろいろな文書に通用するか確かめられないためです。

## 進め方

- コピーの中身は、できるだけ直しません。ただし、文書どうしで食い違っているところは直します。
- 書き方の決まりを作り、種類ごと（スキル・レビュー役のエージェント・決めたこと・issue・PR・レビュー結果）に見本を作ります。
- やることは、このリポジトリの issue に置きます。

## やることの一覧

上から順に進めます。一件ずつ、一つのセッションで終わる大きさです。

| 順 | やること | 種類 |
| --- | --- | --- |
| 1 | 文書どうしの食い違いを洗い出して直す | 直す |
| 2 | 書き方の決まりの最初の版を作る | 作る |
| 3 | 用語集を一般の言葉に寄せ、文書からリンクを張るかを決める | 作る・決める |
| 4 | 親の README から一続きに読めるよう、入口と全体の図を作る | 作る |
| 5 | 決めたこと・改善案を 1 件 1 ファイルに分け、一覧を作る | 直す |
| 6 | スキルとレビュー役のエージェントの見本を作る | 見本 |
| 7 | 決めたこと・issue・PR・レビュー結果の見本を作る | 見本 |
| 8 | 工程ごとにスキルを分けるかを決める | 決める |
| 9 | 文書を親に集めるか、子にも置くかを決める | 決める |
| 10 | コーディング規約・おすすめの設計パターンが要るかを決める | 決める |

### 1. 文書どうしの食い違いを洗い出して直す

決まりを作る前に、材料の中で互いに食い違っているところを直します。食い違いが残っていると、どちらに合わせた決まりなのかが分からなくなるためです。

### 2. 書き方の決まりの最初の版を作る

誰が読むか、文の形、見出しや表の使い方などの決まりを作ります。以降の見本は、この決まりに沿って作ります。

### 3. 用語集を一般の言葉に寄せ、リンクを張るかを決める

内輪の言葉は一般の言葉に置き換えます（例：いまの文書で「関門」と呼んでいる、終わる前に必ず通す確かめ → CI）。文書から用語集の項目へリンクを張るか（Wiki のように）は、手間に見合うかを試して決めます。

### 4. 入口と全体の図を作る

親の README から、上から下へ一続きに読み進められるようにします。全体は図で見せます。

### 5. 決めたこと・改善案を 1 件 1 ファイルに分ける

いまは `docs/decisions.md`・`docs/ideas.md` に積み上がっています。1 件 1 ファイルに分け、種別と優先順位を持たせた一覧を作ります。

### 6・7. 見本を作る

種類ごとに、見本になるものを一つずつ作ります。issue と PR は、このリポジトリで本物を作って試します。

### 8. 工程ごとにスキルを分けるかを決める

いまは要件・設計・実装・テストの工程ごとにスキルを分けていますが、実際は最後のレビュー一つである程度回っています。分ける利点、レビューしやすくなるか、同じことを何度も書くことにならないかを比べて決めます。qata の [#59](https://github.com/masakazu2025/qata/issues/59)（工程ごとに別のエージェントで確かめる）と重なります。

### 9. 文書を親に集めるか、子にも置くかを決める

いまは文書がほぼ親に集まっていて、子には決めたことも内部の仕組みの説明もほとんどありません。親の役目は全体を見渡すことなので、子のことは子に書くべきではないか、保守の仕方と合わせて決めます。

### 10. コーディング規約・設計パターンが要るかを決める

ないと、書き方やフォルダの分け方がそろいません。qata の [#24](https://github.com/masakazu2025/qata/issues/24)（コードの書き方の決まり）と重なります。
